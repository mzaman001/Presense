# Phase 3a: Do Space Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Bring the Do space and its shared component dependencies into §4 flat-surface compliance. Do's own page logic (board/today/calendar views, single-pass bucketing, dynamic-import code-splitting) is already well-engineered per spec §3 and stays unchanged — this plan is a visual/token pass, not a restructure.

**Architecture:** Do's page (`src/app/(app)/do/page.tsx`) is the entry point, but the real violations live in shared components it renders: `TaskCard.tsx` (gradient swipe-reveal layers, a motion blur filter, a glow box-shadow, and several hardcoded colors — used by Do AND Home's "Up Next" list, so fixing it here benefits both), `EmptyState.tsx` and `TaskAddPanel.tsx` (each with one or two hardcoded white-rgba values that silently assume dark mode and would render wrong/invisible in light mode). `PageHeader.tsx`, `SegmentedControl.tsx`, and `Badge.tsx` were checked and are already clean — no changes needed there.

**Tech Stack:** Next.js 16.3, React 19, Framer Motion (drag/swipe gestures — kept, this is interaction logic not surface styling), TanStack Query, Tailwind v4.

**Spec:** `docs/superpowers/specs/2026-09-13-design-system-overhaul-design.md` §4 (flat surfaces), §3 ("Do — unchanged in scope. Already well-engineered").

## Global Constraints

- No gradients, glows, or glassmorphism (blur) on any surface. This plan draws a line between **surface styling** (backgrounds, borders, box-shadows — must be flat) and **transient motion** (a card's own opacity/scale/position changing during a 250-300ms interaction transition — Framer Motion drag/swipe gestures are kept, since removing task interactions isn't in scope; only the `filter: blur(...)` step of TaskCard's existing transition is removed, per the ruling in Task 1).
- No hardcoded hex colors, bare Tailwind palette classes (`red-400`, `green-400`, etc.), or hardcoded `rgba(255,255,255,...)`/`rgba(0,0,0,...)` values — use `var(--token)`. Hardcoded white/black-based rgba values are a correctness bug, not just a style violation: they assume dark mode and render wrong in light mode.
- Every task ends in a state where `npm run lint`, `npx tsc --noEmit`, and `npm test` are clean.

## File Structure

- Modify: `src/components/features/TaskCard.tsx` — flatten swipe layers, remove blur/glow, tokenize colors. New priority-color tokens added to globals.css are consumed here.
- Modify: `src/app/globals.css` — add `--priority-urgent`/`--priority-high`/`--priority-medium` tokens (no existing token covers this axis — priority is a different semantic dimension from `--status-*`, which already covers a comparable multi-hue precedent, so this follows the established pattern rather than inventing a new one).
- Modify: `src/components/ui/EmptyState.tsx` — one hardcoded rgba fix.
- Modify: `src/components/features/TaskAddPanel.tsx` — two hardcoded rgba fixes (scoped fix, not a full redesign of this 1200-line panel — see investigation notes).
- Modify: `src/app/(app)/do/page.tsx` — hardcoded rgba fixes, archive-toggle and category-filter pill buttons re-tokened.
- No changes to: `PageHeader.tsx`, `SegmentedControl.tsx`, `Badge.tsx` (confirmed already clean), `CalendarView.tsx` (confirmed already clean).

## Investigation Notes (read before starting)

- **`TaskCard.tsx` is a cross-cutting component** — used by Do's board/today views AND Home's "Up Next" list (`src/app/(app)/page.tsx`). Fixing it here benefits both surfaces, the same pattern as flattening `GlassCard` during the Home phase.
- **Priority colors have no existing token.** `--status-*` tokens (overdue/today/upcoming/someday/done/danger) cover a *status* axis; TaskCard's priority dot covers a separate *priority* axis (urgent/high/medium/low) currently hardcoded as `#ef4444`/`#eab308`/`#22c55e`/`var(--text-muted)`. Since `--status-*` already establishes that this design system permits a small multi-hue semantic palette (not literally "one color everywhere" — that constraint is about decorative/brand elements), this plan adds three matching `--priority-*` tokens rather than collapsing priority signal to monochrome, which would remove real functional information users rely on.
- **`TaskAddPanel.tsx` is 1209 lines with 10 hand-rolled `<button>` elements and zero usage of the shared `Button` component.** Grepped for actual spec violations (gradient/blur/glow/hardcoded-hex): found exactly two hardcoded `rgba(255,255,255,...)` instances, nothing else. This plan fixes those two specific violations and does NOT attempt a wholesale migration of all 10 buttons to the shared `Button` component — that's a much larger, separately-scoped effort with its own review surface, out of proportion to what this plan's investigation actually found wrong. Flag it as a known follow-up, not silently expand this plan's scope to cover it.
- **The motion-blur-during-transition question**: TaskCard's enter/exit animation includes a `filter: blur(1px)` → `blur(4px)` step (a 250-300ms transition, not a static surface). Ruling: this is removed anyway (Task 1) — not because transient motion blur is definitely prohibited by §4 (which is about surfaces), but because a cleaner flat opacity/scale-only transition achieves the same "this card is leaving" signal without needing to litigate the motion-vs-surface distinction, and matches the "no blur anywhere" instinct the rest of this phase has followed. Documented as a judgment call, not a forced reading of the spec.
