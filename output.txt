Pattern Analysis
The 5 Root Causes (not the symptoms)
Root Cause 1: The database layer was never verified before the UI was built
Every "adding does nothing" bug traces back to the same failure: SQL migrations were written and assumed to work without being verified in isolation first. When they broke silently, the UI had no error handling to expose what failed — so everything looked like a UI bug but was actually a DB bug. The pattern: schema → UI → discover it doesn't save → fix schema → UI still shows stale state because realtime wasn't wired. This sequence will repeat on every new feature if not stopped at the source.
Root Cause 2: Features were built as isolated units, not as parts of a connected system
The spec clearly defines 20 connection points between features. But in practice, each space (Do, Think, People, Explore, Locations) was built as its own mini-app with its own data fetch, its own save logic, and its own state — none of which talked to each other. The Home dashboard failed as a result because it had nothing to aggregate. People briefings never appeared because the People space never wrote data the Home could read. This is the "app of its own" feeling — because architecturally, they were.
Root Cause 3: The spec was written but never enforced as a build contract
The PRD (presense_doc.js) is thorough. But each time a new feature was built, it was built from scratch from memory rather than by reading the spec first. This is why the NLP date path was wrong (dates[0].start vs dates[0].dates.start), why "Add Person" was decorative, why "Focus Now" had no explained logic, why IF-then tags were confusing. None of these are hard problems — they are skipped-spec problems. The spec exists. It must be the primary input to every build session.
Root Cause 4: No error boundaries, no loading states, no feedback loops
When something fails (DB insert, NLP parse, realtime subscription), the user sees... nothing. The UI closes. The button does nothing. There are no toasts, no error messages, no console logs surfaced to the user, no retry mechanisms. This means every bug is invisible until the user reports it. The app has no observability. Silent failures in a personal productivity app are uniquely destructive — if the user captures something and it silently disappears, they lose trust in the system permanently. Trust is the entire value proposition.
Root Cause 5: The onboarding gap means the app has no personalisation context
The app skips from login directly into the dashboard. It does not know the user's name, working hours, timezone, or which spaces they care about most. Every piece of text is generic. The nudge notifications fire at a default time without knowing when the user is awake. The Home dashboard greets nobody. Without onboarding, the app is a framework — not a personal second brain. The entire premise of the app (it is built specifically for YOU) is immediately violated the first time you open it. SECTION 1
The Problem — User Psychology & Research Foundation

PRESENSE is not a generic productivity app. It is purpose-built for a specific, well-researched set of cognitive difficulties. Every design and feature decision below traces back to this psychological profile.

1.1 The User Profile
The primary user is a college student with these self-reported difficulties:
Forgetting what people say during conversations — often within the same day
Forgetting tasks, appointments, and where physical items are placed
Procrastinating on all types of tasks — daily, not occasionally
Overthinking where to start tasks — not motivation failure but initiation failure
Zoning out during activities (gym, lectures, conversations) so information does not fully encode
No natural productive window during the day
Only moving when external deadlines from others apply pressure
Previous apps all failed because the user forgot to open them
Wants step-by-step guidance, full feature control, and a beautiful frictionless interface

1.2 Research Foundation
Cognitive Disengagement Syndrome (CDS / Sluggish Cognitive Tempo)

CDS explains zoning out during gym sessions with a friend (only registers information when social presence manages it), forgetting conversations, and having no natural productive window. The intervention: externalise all cognitive load. The app becomes the arousal system the brain does not self-generate.

Prospective Memory Failure (Guynn et al.)

This is why every notification in PRESENSE specifies both event and action. 'OS exam tomorrow — Open Chapter 3 to page 47 right now.' Never just 'OS exam tomorrow.' This is non-negotiable in the notification design.

Implementation Intentions (Gollwitzer, 1999)

Every task in PRESENSE prompts the user to set an if-then anchor at creation time: 'When I sit at my desk after dinner, I will open my OS notes to page 47.' The user fills this in guided by a prompt. Research shows self-generated if-then plans are more effective than externally generated ones — so this being user-filled is actually better than AI-generated.

Executive Function Deficit & External Scaffolding (Barkley)

The Zeigarnik Effect

Quick Capture exists specifically to close Zeigarnik loops instantly. The moment something is captured, the brain can release it. This also explains why capturing random thoughts, plans, and interesting things is a core feature — it reduces the background noise of open loops.

Building a Second Brain — Tiago Forte (CODE Framework)

The four spaces of PRESENSE (Do, People, Think, Explore) directly implement CODE. The Sunday Digest resurfaces Explore items. The Think space enables ongoing reflection without requiring upfront organisation.

Body Doubling & Social Accountability

The 10-minute Start session is built on this principle. Rather than asking the user to commit to finishing a task, it asks for just 10 minutes of presence. The initiation threshold drops to near zero. Once started, momentum carries the work forward.

Design System

4.1 Design Philosophy
PRESENSE uses a dark-first design drawing from three reference aesthetics. First: the ambient gradient atmosphere of high-end apps — soft radial gradient blobs give the background life rather than a flat dark colour. Second: the restrained information density of Linear and Vercel — glass cards with ultra-thin borders, a single accent colour, generous breathing room. Third: confident typographic hierarchy — bold display text that earns its size. Together they create a space that feels alive but quiet, designed to reduce cognitive noise.

hourly_check.ts: Queries items for tasks hitting the 72h, 24h, 6h, 1h, overdue thresholds. Checks notification_log to prevent duplicates. Sends Web Push via /api/push/send. Logs each send. Free tier: 500K invocations/month. Hourly runs = 8,760/year — well within limit.
